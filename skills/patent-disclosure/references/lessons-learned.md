## 补点方法（用户给出部分创新点、需撰写者补齐时）

1. 先区分**表示手段**与**测量方法**：把数据组织成网络/图谱通常只是表示手段，真正可主张的往往是"如何用该表示完成测量"的那一步。
2. 依次扫描源材料中的方法学增量，按可专利性排序：
   ① 测度构造（指数如何定义、归一化方式、阈值语义）；
   ② 传导/失效机制建模（序贯移除、级联失效、依赖判定）；
   ③ 数据到标准体系的映射与校验闭环（模型级联 + 阈值 + 交叉校验）；
   ④ 稳健性校验设计（对照实验、统计量）。
3. 补出的创新点必须满足三要素闭环（技术手段 → 技术问题 → 技术效果），且能在源材料中找到依据；**不得**为凑点而虚构模块。
4. 交付时用一句话说明该点的必要性（它解决了另外两点解决不了的什么问题），便于代理人理解布局意图。

## 测量类发明的客体强化（指标构建 / 暴露度 / 风险指数等）

- 把**测量问题写成数据处理技术问题**：非结构化文本难以转化为标准化可比对象、线性加权丢失结构信息、口径不一致导致不可复现——而不是"政策需要指标"。
- 把**指数本身写成技术效果**，并给出取值域与语义（如 E_j∈[0,1]，1=首轮失效、0=末轮失效），而不是"有利于政策制定"。
- 把**指标计算过程写成技术手段**：模型微调、向量匹配、阈值过滤、图投影、中心性计算、序贯移除、归一化。
- 保留一个**可验证的技术效果证据**（对照实验、统计量、精度指标），避免通篇只有经济意义。
- 避免出现：纯经济/管理目标作为技术问题；只描述统计意义而无计算步骤；把"评分表"当作技术方案。
- 结尾的"替代方案"要覆盖算法选型、参数阈值、权重映射与承载形式（设备/介质），为权利要求留纵深。

## 转述他人框架类案件的写法（以参照论文为最接近现有技术）

用户提供一篇外语/外域论文作为参照，要求"据此做一个我们自己的（中文/本域）版本"时：

1. **把该论文明确写成背景技术里的最接近现有技术**，逐条列出其架构、模型选型、阈值、验证方式与规模（这些是可核验的事实，抄进背景技术反而强化区别特征）。
2. **继承的通用架构不得当作发明点**：如"先分类后匹配的两阶段""按相似度分层审计定阈值"属于该论文的既有手段，写作时以"现有技术采用…"表述，本案主张点放在**本域适配所产生的技术特征**上。
3. **主张点取自该框架在本域必然失败的地方**，典型四类：
   - 语料侧：语言/表述差异导致的分类失真（如中文"同岗异名""异岗同名"）；
   - 标准侧：目标体系由单一变为多套、需要跨语言语义对齐与条目对照表；
   - 口径侧：本域数据的字段缺失、时间口径不同（如以招聘起止日期界定活跃月份）；
   - 合规侧：本域公开数据的披露约束（最小单元格、差分隐私、去标识化）。
4. **技术效果必须对应"框架迁移失败点被解决"**，逐条写因果，不写"填补国内空白"这类无技术含量的表述。
5. 若同批材料拆成多案，须在各案中互相注明为平行申请，并划清权利要求边界（模型构建案 vs 测量应用案），避免一案的实施方式成为另一案的自证现有技术。

## 读料小技巧

- PDF 提取文本若被 `read` 判为二进制：先删除 `\x00`–`\x1f` 控制字符再读。
- docx 用 `tools/extract_docx_text.py`；表格会被渲染为"【表格开始/结束】+ `|` 分隔行"，模型表、验证表照此读取即可。
- 论文中的 Word 公式在纯文本里会串行（如上标丢失），涉及公式时以论文正文文字描述为准，并在使用处标注待核实。
- **取上游大文件不要吞进上下文**：jsdelivr 常把请求重定向到 `raw.githubusercontent.com`（web_fetch 不跨域跟随，需改用 API contents 端点）；API 返回的 JSON 里 `content` 是 base64，若结果被 spill 到临时文件，直接用 python 解析该 JSON 并 base64 解码落盘即可，字节数与上游一致；单文件 ≥20KB 时优先派子代理代取，主上下文只收字节数对照表。
- 随附外部脚本后**必须冒烟运行**（`--help` + 一个最小样例），确认依赖满足（本机有 Pillow/numpy/matplotlib，无 graphviz/inkscape/pandoc）。
- 引擎会把长标签换行拆成多个 `<text>` 元素，图文核对须**去空白后整串比对**（`tools/verify_figures.py` 已内置）；判断框标签故意不带步骤号，避免编号语义混乱。
- **发布/同步前先验证，不要凭字节哈希下结论**：跨平台（Windows 写、git 归一化、Linux 取回）时行尾会变，用"关键内容标记是否存在"判定版本是否一致；`scripts/vendor_upstream.py check` 报 differs 时先看 CRLF 计数。
- GitHub 只对**标准全文**的 `LICENSE` 识别许可证；任何附加说明都会让它变成 NOASSERTION——附加说明放 `NOTICE.md`。
